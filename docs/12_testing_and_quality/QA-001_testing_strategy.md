# QA-001 — Testing Strategy

Financial correctness is proved by tests whose expected values come from specifications and human-prepared worked examples, not from the code under test. Tenant isolation is proved by negative tests on every build.

## 1. Mandatory test types

| Type | What it proves | Tooling | When |
| --- | --- | --- | --- |
| Unit | Functions and domain rules | Pytest, Vitest | Every PR |
| Financial calculation (expected-result) | Engine outputs equal independently prepared values | Pytest + versioned test-pack files (CSV/YAML) under `tests/financial/` | Every PR touching engines |
| Property-based | Invariants hold for random inputs (e.g., every batch balances; units × NAV ≈ amount within rounding; NAV reconstruction equals stored NAV) | Hypothesis | Every PR (fast profile), nightly (deep profile) |
| Integration | Module + database + outbox together | Pytest + Testcontainers (PostgreSQL, Kafka, Redis) | Every PR |
| API contract | Implementation matches OpenAPI; consumer expectations hold | Schemathesis + contract tests | Every PR |
| Database | Migrations apply/rollback; constraints, triggers, RLS behave | `database/tests/` SQL + Pytest | Every PR touching `database/` |
| Tenant isolation | No cross-tenant read/write via DB, API, cache, object store, events, AI retrieval | Dedicated suite (extends DBT-000 T1a–T1g) | Every PR (CI blocks) |
| Security | SAST, dependency scan, secret scan, DAST on staging, pen test | Semgrep/Bandit, dependency audit, gitleaks, OWASP ZAP | Every PR / nightly / per release |
| Performance | NFR targets (e.g., pre-trade check p95 < 300 ms) | k6 / Locust; production-size synthetic data | Per release, T1/T2 |
| End-to-end workflow | WF-001…WF-017 through UI and APIs | Playwright | Nightly + release |
| Regression | Previously fixed defects stay fixed | Every bug fix adds a test with the defect ID | Every PR |
| Historical replay | Re-running a past date with stored inputs gives stored outputs | Replay harness | Nightly on sampled dates |

## 2. Coverage targets

| Code | Line + branch coverage |
| --- | --- |
| T1 financial engines (FE-01, 02, 03, 04, 06, 07, 09) | ≥ 95%, plus expected-result and property-based suites (master prompt §16) |
| T2 engines and services | ≥ 85% |
| Other backend | ≥ 75% |
| Frontend | ≥ 70% on logic; Playwright for flows |

Coverage is a floor, not a goal; a high number with no expected-result tests does not pass G5.

## 3. Test data

- Synthetic only; generated by documented scripts in `scripts/` and `database/seeds/`.
- No production data or real investor PII in any non-production environment.
- Financial test packs are version-controlled, reviewed by a domain expert and carry the spec section they test.

## 4. Gate mapping

| Gate (GOV-004) | Test evidence |
| --- | --- |
| G3 | Unit, integration, contract, database, tenant-isolation, static and security scans green; coverage met |
| G4 | E2E workflows green in integration environment |
| G5 | Expected-result packs, property tests, historical replay; T1 parallel-run report |
| G6 | Performance, backup-restore, failover tests |

## 5. Honest reporting

A test reported as passed must have been executed, with a run link. Skipped or not-run tests are reported as such (master prompt §20 Step 6).
