## AMC OS Review Agent — advisory review

**PR:** local branch `wp4-step16ab-review-fixes` (base `origin/wp4-step16a-ddl-foundation-platform-identity-master` b6eedb7; review file reviews/STEP-16ab_round3.md) · **Step / WP:** GOV-006 Step 16, part a, fix round (WP4) · **Reviewed at:** 90553d46f204847dfc6beaa965c7b0f7e49755d3

**Verdict (advisory):** BLOCK
The new commit-time request check treats the database's own carried-forward rows as new uses of an old request. As a result, a grant or scope row created through a request can no longer be ended from a later date, so a normal revocation fails. Separately, a user can approve a scope change to their own grant.

| 1 | Blocker | database/ddl/DDL-001_step16a_foundation_platform_identity_audit_master.sql:1389-1404, :1437-1444 (with `bt_is_continuation` :117) | **A grant or scope row that came from a request cannot be ended or corrected from a later date.** When an END closes a version, the database writes a "continuation" row: a copy of the part before the end date, which keeps the old `request_id`. The new deferred constraint triggers run at COMMIT, at trigger depth 1. At that depth `platform.bt_is_continuation` always returns false, because it needs depth ≥ 2. So the continuation is taken as a new use of the old request. That request is already `APPLIED`, so the commit fails with `REQUEST_NOT_APPROVED … applied by another transaction`. I reproduced this three times as `amc_app`. (a) Grant `c44…04` had a version `[2027-01-01,)` from APPLIED GRANT request `e44…03`. An approved REVOKE `e44…04` with `END 2027-02-01` was refused at commit, and the user keeps the role. (b) Scope row `SCHEME=S1` `[2026-11-01,)` came from request `e44…01`. An approved CHANGE_SCOPE "remove S1 from 2026-12-01" was refused at commit. (c) A plain signed new version `[2027-06-01,)` on the same grant, which follows BT-1, was refused the same way. DBT-001 misses this because every END it runs on a request-linked row ends on the row's start date, so no continuation is written. This breaks revocation (D-76) for the normal path, where grants come from requests. | In `tg_mark_request_applied`, do not rely on `bt_is_continuation` at commit. Either skip rows whose `recorded_at` equals the `superseded_at` of a closed row with the same content (check the data without the depth test), or decide at insert time and record the result. Simplest: run the completeness check only for rows that `tg_scope_attribute_request` / `tg_user_role_no_self_grant` / `tg_grant_closure_request` actually checked. Have those BEFORE triggers record the request ID in a transaction-local list, and have the deferred trigger read only that list. Add DBT tests that end a request-created grant and a request-created scope row from a date after their start, and that insert a correcting version over a request-created grant. |
