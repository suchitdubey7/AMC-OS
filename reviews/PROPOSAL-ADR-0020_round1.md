## AMC OS Review Agent — advisory review

**PR:** branch `proposal/adr-0020-schema-moves-db-roles` (vs `origin/wp4-step15-canonical-data-model`) · **Step / WP:** none of its own. This is an owner-requested Draft ADR-0020 to collect what EA-003 §7, EA-005 §9, EA-007 §13 and DA-001 §8 deferred (WP4, before Step 16). · **Reviewed at:** a9d44e108304552e57fcc9fade13294b91418472

**Verdict (advisory):** RECOMMEND CHANGES
The ADR covers the deferred items and its main PostgreSQL claims are correct. But six Major gaps remain. As written, the break-glass policy would return no rows. The SECURITY DEFINER and policy-role design is not complete. Two scope items are missing (the analytics extract worker and removal of a tenant's ordinary rows). The column-only tenant-list grant is undone by another part of the ADR.

### Findings

| --- | --- | --- | --- | --- |
| 1 | Major | ADR-0020:113-115 (§7.3, §7.4); DA-001:267 | The break-glass permissive policy checks `identity.break_glass_grant`, but that table is itself a tenant table with forced RLS. Its `tenant_isolation` policy applies only to module, worker and tool roles (§7.1). So the break-glass login sees no grant rows, and the policy returns 0 rows. I tested this on PG 16.15. With an unprotected grant table the login saw only the granted tenant's rows. Once the grant table had forced RLS with a policy for module roles only, it saw 0 rows. The "[VAL, tested]" result in §7.4 must have used a grant table without RLS, and the ADR does not say so. | Say how the grant lookup works under forced RLS. For example, add a policy on `identity.break_glass_grant` for `amc_breakglass` that matches the grant row whose login name equals `current_user`, with `SELECT` on that table only. Then add this case to Validation test 4. |
| 2 | Major | ADR-0020:82-90, :96, :109 (§5.2, §5.3, §6, §7.1) | Under FORCE RLS, the roles that own SECURITY DEFINER functions (`amc_audit_writer`, `amc_audit_import`, `amc_tenant_removal`) do not own the tables, so RLS applies to them. §7.1 limits `tenant_isolation` to "module, worker and tool roles" and never says whether these roles are included. If a role has no policy, every insert and delete it makes is refused. Tested: the definer insert failed with "new row violates row-level security policy". The same applies to the roles §2.6 keeps (`amc_readonly`, `amc_auditor`, `amc_ai_agent`). After §7.1 they would silently see no rows, and `amc_ai_agent` could no longer insert into `ai.tool_call_log`, which §2.6 says is unchanged. The ADR also does not say where the removal procedure gets its tenant context. | List every role in the `TO` list, or give it its own policy, and say how each one sets its tenant (for example, the removal procedure uses `SET LOCAL` from the authorisation row). Add a DBT test for each role. |
| 3 | Major | ADR-0020:82-90, :96 (§5.2, §5.3, §5.5, §6) | The SECURITY DEFINER design leaves out two standard safeguards. (a) PostgreSQL grants `EXECUTE` on new functions to `PUBLIC` by default (checked: `has_function_privilege` returned true for an unrelated role). §5.5 says only the platform-tools login can run these functions, and §6 says only modules can write audit, but neither holds without `REVOKE EXECUTE … FROM PUBLIC`. Until then, any role (break-glass, `amc_ai_agent`, `amc_readonly`) could call the audit write function. (b) There is no fixed `search_path` (PostgreSQL docs, "Writing SECURITY DEFINER Functions Safely"). Also, unlike removal, nothing in the database ties an audit import to an approved run record. | Require `REVOKE ALL ON FUNCTION … FROM PUBLIC`, explicit `GRANT EXECUTE`, and `SET search_path = pg_catalog, <schema>` on every definer function. Have the import function check an approved `audit.import_run` or migration record. Extend Validation tests 7 and 8 to calls from `PUBLIC`. |
| 4 | Major | ADR-0020:30 (§2.2), :69-71 (§4); DDL-000:86 | §4 gives worker logins only `SELECT (tenant_id, status)` on `platform.tenant`. But §2.2 gives every module role `SELECT` on the whole `platform.tenant`, and the relay and scheduler run under module roles. The column limit therefore has no effect. `platform.tenant` has no RLS, so every module role can read every tenant's `legal_name`, `sebi_reg_no` and `kms_key_ref` in a shared cell. DDL-000 says this table is "visible to platform admin only". This leaks other tenants' metadata, which matters under master prompt §3.4. | Make §2.2 grant only the columns modules need (or a view with one row per current tenant). Say whether `kms_key_ref` and `legal_name` are visible to modules. Add a grant test. |
| 5 | Major | ADR-0020:30 (§2.2), :59-71 (§4) | §2.2 adds a D16 Reporting extract role that reads every schema. This is a system worker that reads business data for every tenant, but it is not in the §4 table. That contradicts "the following workers are the **only** exceptions" and "No worker loops over tenants to read business data". It also does not say where its tenant context comes from or how it gets past forced RLS. | Add the extract worker to §4: where its tenant comes from, one tenant per transaction, which policies apply, and that it is read-only. Or move the D16 extract design to DA-002 and say so. |
| 6 | Major | ADR-0020:84-88 (§5.3); EA-005:67, :178 | EA-005 §2.1 and §9 ask ADR-0020 to record the "removal" tool, which "removes a tenant's rows". The ADR covers only the protected rows (posted journals, audit). It does not say which role deletes the tenant's other rows in all 23 schemas: module roles get `DELETE` only for purges (§2.1). It also does not say that `amc_tenant_removal` deletes from schemas it does not own, which is an exception to §5.1's "no role writes another schema". | Add the removal of ordinary rows to §5 (for example, each module's own removal function run under its own role, called in order like seed and import). State the cross-schema delete exception for `amc_tenant_removal`. |
| 7 | Major | ADR-0020:111 (§7.2); EA-005:139 | EA-005 §6 passes "login handling" to ADR-0020. The ADR does not say which role creates and drops the per-grant logins and grants them `amc_breakglass`, how the credential is issued, or which role ends their sessions. In PostgreSQL 16 creating roles needs `CREATEROLE` with ADMIN OPTION on `amc_breakglass`, and ending other sessions needs `pg_signal_backend` or equivalent. Both are high-risk rights that the role model must name. | Name that role (for example, an Identity or break-glass provisioner with `CREATEROLE` and ADMIN on `amc_breakglass` only, and no other rights). Say how credentials are delivered. Add a test that the provisioner cannot grant any other role. |
| 8 | Minor | ADR-0020:33 (§2.4) vs :82, :86, :96 | §2.4 says "All tables, functions and policies are owned by `amc_migration_owner`". §5.2, §5.3 and §6 give definer functions other owners. §2.4 is also true but incomplete: FORCE RLS does not stop the owner from running `ALTER TABLE … NO FORCE`, disabling triggers or dropping policies. That makes the owner's credential as sensitive as `BYPASSRLS`. | Change to "except the definer functions in §5–§6".
