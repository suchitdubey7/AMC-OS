## AMC OS Review Agent — advisory review

**PR:** branch `wp4-step16b-ddl-product-front-office` (base `wp4-step16ac-review-fixes`) · **Step / WP:** GOV-006 Step 16, part b (WP4) · **Reviewed at:** 6020f44

**Verdict (advisory):** RECOMMEND CHANGES
The DDL applies cleanly and all claimed tests pass. But the database still allows three things it is meant to stop: a cancelled outbound instruction can be sent, a call-back can name a made-up person, and an amended order can leave compliance on the old version's result.

### Findings
| # | Severity | File:line | Finding | Suggested fix |

| 1 | Major | database/ddl/DDL-002_…sql:1745-1746, 1774, 2127, 2233 | The comment says a business status other than PENDING needs an acknowledged delivery, "except CANCELLED of a leg that was never sent". The CHECK actually allows `CANCELLED` in any delivery state. I tested it on `execution.broker_order`: READY → SENT → UNKNOWN_OUTCOME, then business status CANCELLED, then delivery UNKNOWN_OUTCOME → READY → SENT were all accepted. The row ends as `SENT` + `CANCELLED`. The same CHECK is on `settlement.instruction` and `settlement.payment_instruction`. So a payment or broker order whose outcome is unknown can be marked cancelled, and a cancelled one can then be sent. That conflicts with INT-001 §6 (OUT2, unknown-outcome handling) and with the file's own comment. | Allow `CANCELLED` only while `delivery_state = 'READY'`, or after ACKNOWLEDGED through the business transitions. Refuse any delivery move out of READY once the business status is not `PENDING`. Add DBT tests for all three instruction tables. |
| 2 | Major | database/ddl/DDL-002_…sql:2047-2054, 2080-2086 | The call-back control on `settlement.ssi_version` and `settlement.scheme_bank_account_version` only checks `callback_by <> maker_user_id`. `callback_by` is a typed-in value that is never checked. I tested it: an SSI version with `callback_by = gen_random_uuid()` (no such user) was accepted. So a maker can record a fake call-back on a bank-account or SSI change, the most fraud-prone data in settlement. DA-001 §11 (16b row) and PRD-007 BRL-D07-001 present this as enforced. | Require `callback_by` to be an active, non-service user of the tenant (the same check as `platform.tg_set_actor`). Better still, record the call-back as a separate act by the acting user. Add a test with an unknown or service user. |
| 3 | Major | database/ddl/DDL-002_…sql:1479-1491; DA-001 §11 row `trading."order"` | Under the Q81 assumption an order in `PENDING_COMPLIANCE` can be amended to a new version with no state move. Nothing in the database ties leaving `PENDING_COMPLIANCE` to a result for the current version. I tested it: v1 PASS was stored in `compliance_result_ref`, the order was amended to v2 (quantity 500 → 50,000, cause AMEND), and the move to `PENDING_APPROVAL` was accepted with no v2 result. DM-6's stated aim is that "the compliance result of the old version never covers the new one". The new no-move amend path reopens that gap, including a race with an in-flight check. | When moving out of `PENDING_COMPLIANCE` (and `OVERRIDE_APPROVED` → `PENDING_APPROVAL`), require a `trading.compliance_result_ref` row for `NEW.order_version`. That is the same schema, so M4 allows it. Add a DBT test. Alternatively, record in DA-001 §11 that only the application enforces this, and add it to Q81. |

This does not match the "author is the acting user, fixed afterwards" rule that `tg_set_actor` applies to other author columns. | Put `platform.tg_set_actor('created_by')` on these tables, or say in DA-001 §11 that `created_by` is informational only. |
