## AMC OS Review Agent — advisory review

**PR:** local branch `wp4-step16a-ddl-foundation-platform-identity-master` (review round 1) · **Step / WP:** GOV-006 Step 16, part a (WP4) · **Reviewed at:** d54a7a1951acc2632dbf9c6d413a76f52d09a69c

**Verdict (advisory):** RECOMMEND CHANGES
The schema scope matches DA-001 §4.1–§4.4, the ADR-0020 items are correctly left out, and both test files pass on PostgreSQL 16.15. But adversarial runs as `amc_app` found 8 Major problems:
- Corrections cannot be recorded at all for the two date-keyed bi-temporal tables.
- The application can set the bi-temporal knowledge timestamps itself.
- A forward-dated version silently removes current master data.
- The application can write its own entitlements.
- Two configuration versions can be effective for the same dates.
- A race condition in the configuration trigger lets a value be added after validation.
- Two product-level lists can still be written by the application.
- Tests are missing for the paths above.

| 1 | Major | database/ddl/DDL-001_step16a_foundation_platform_identity_audit_master.sql:459, :1171 | **Corrections are impossible on `platform.business_calendar` and `master.security_schedule`.** Their "one current row per key" rule is a partial unique index. PostgreSQL checks that index when the row is inserted, which is before the AFTER INSERT `bt_supersede` trigger can close the old row. Reproduced as `amc_app`: a second row for `NSE_EQ` / 2026-12-25 fails with `duplicate key value violates unique constraint "business_calendar_current_ux"`. The same happens for a corrected coupon row (`security_schedule_current_ux`). The guard also refuses a manual `superseded_at` update, so these tables have no correction path at all. This contradicts M7, DM-1 and DA-001 §11 ("no overlap … checked at commit"). | Replace both indexes with `EXCLUDE (tenant_id WITH =, calendar_code WITH =, cal_date WITH =) WHERE (superseded_at IS NULL) DEFERRABLE INITIALLY DEFERRED` (and the equivalent for the schedule). | 2 | Major | DDL-001:176-183 (make_bitemporal), :48-62; DBT-001:195 | **`recorded_at` and `superseded_at` can be set by the application.** M8 says system time is "set by the database". Reproduced: (a) inserting a version with `recorded_at='2026-02-01', superseded_at='2026-03-01'` is accepted, so the application can forge what was "known" on a past date (an "as known on X" query returns the forged value). Reproduced with two sessions: session A inserts a value while the version is `DRAFT` and holds its transaction open; session B moves the version to `VALIDATED` and commits; A commits. The result is a `VALIDATED` version with a value that was never validated. | Read the version with `SELECT status … FOR SHARE` (or `FOR UPDATE`) in the trigger. |
